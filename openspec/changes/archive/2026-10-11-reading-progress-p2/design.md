# Design

## Context

См. [аудит](../../../../docs/READING_P2_AUDIT.md) и proposal.md. P1 уже связывает ReadingSession,
Trainer, Staff и один Redux slice; новый слой не должен создавать альтернативные часы или базу.
Владелец согласовал P2 11.10.2026 и предложил IndexedDB для растущей истории. Реализация разрешена;
прогресс переносится в существующую IndexedDB, настройки других подсистем не мигрируются.

## Goals / Non-Goals

**Goals:** общий расширяемый контракт события, чистая статистика, воспроизводимая адаптация пяти нот
и безопасная миграция. Сохранить обычный seed v1 и активное состояние при просмотре сводки.

**Non-Goals:** воспроизведение слуховых заданий, второй PracticeSession, изменение Take или
CourseProgress, серверная аналитика, новые зависимости. P3 следует отдельным изменением.

## Decisions

### Владение

`src/reading` владеет чистыми расчётами и типами; подмодули `progress.ts`, `adaptation.ts` и
`progressTypes.ts` создаются при реализации, с тестами рядом. Общая оболочка события содержит
skillId, exerciseId, runId, attemptId, inputSource; discriminated union различает note-reading,
rhythm, aural-interval и chord metrics. P2 реально создаёт только note-reading. Не вводить пустые
сервисы будущих навыков: типы защищают контракт, существующий slice владеет данными.

`ReadingSession` экспортирует фактические события помощи и монотонные времена. Оболочка создаёт
уникальный runId и календарные startedAt/completedAt; startedAt фиксируется при первом реальном
предъявлении ноты, completedAt включает дату завершения, а реакция считается по прежним активным
интервалам. Идентификатор атаки — runId + последовательный индекс принятой атаки. Поздние callback
остаются защищены идентичностью запуска.

UI получает готовые сводки через app hooks; агрегация не выполняется в JSX. Она пересчитывается при
изменении истории/фильтра, не на каждом frame. XML строится один раз из высот новой серии; снимки
подсказок не меняют MusicXML и не добавляют рендер OSMD.

### Метрики и политика

Сводки разделяются по назначению и источнику. Профиль адаптации одиночного чтения объединяет обычные
одиночные, адаптивные и сбалансированные проверки; фразы имеют отдельный профиль и адаптивную
генерацию в этом P2 не получают. Игрок выбирает «все источники» либо конкретный; этот фильтр
сохраняется и входит в план следующей серии.

Источник наблюдения — источник завершающей правильной атаки. Фильтр включает наблюдение целиком, со
всеми атаками и подсказками; independentCorrect не пересчитывается по отфильтрованным атакам. Так
смешанный ввод не превращает ответ после ошибки в самостоятельную первую попытку.

На каждую ноту берутся последние 20 наблюдений выбранного профиля/источника; минимум 4 для
адаптации. Вес трудности: доля несамостоятельных первых ответов плюс нормированная медиана времени
самостоятельных первых ответов, ограниченная единицей (ориентир 5000 мс). Отсутствующее время не
подменяется нулём; первая компонента остаётся применимой. Эти значения — параметры версии политики.

Адаптивная квота: 2 появления каждой ноты (10), 6 дополнительных высот по весам трудности, 4 по
просроченности. Квота повторения использует календарные последние самостоятельные ответы и интервал
3 дня. Последняя самостоятельная дата хранится отдельно по высоте/источнику и не исчезает при
сокращении окна наблюдений. Шесть слотов трудности распределяются методом наибольших остатков:
floor(6 * weight / sum), оставшиеся слоты — по убыванию дробной части, равенство решается по
возрастанию MIDI. При нулевой сумме используются равные веса. Четыре слота повторения распределяются
циклически по просроченным нотам, от самой давней к свежей; нота без известного самостоятельного
ответа ставится первой, равенство решается по MIDI. При отсутствии просроченных используется равный
вес всех пяти высот с тем же методом наибольших остатков. При недостатке наблюдений по любой ноте
вся серия сбалансирована. Не вводить бинарное «освоено».

Пример: веса C/D/E/F/G = 0/1/0/0/0, все даты свежие. Квота трудности 0/6/0/0/0, повторения
1/1/1/1/0, итог 3/9/3/3/2. Эта серия содержит все пять нот, чаще повторяет D и остаётся одной Song
из 20 событий. Равные веса могут дать дополнительную ноту низшим MIDI; финальное seed-перемешивание
меняет порядок, но не квоты.

Срок отдельной отложенной проверки = completedAt последней сбалансированной проверки + 3 дня.
Учебные ответы могут менять приоритет повторяемых нот, но не сдвигают эту дату. Календарь передаётся
явно из оболочки; генератор не вызывает Date.now/performance.now.

### Детерминизм и журнал предъявлений

План содержит назначение, источник, version генератора/политики и целочисленные квоты пяти высот.
Высоты перемешиваются seed PRNG. Одинаковый план/seed даёт одинаковый XML; обычный v1 остаётся
доступным для воспроизведения старых серий. Проверка не использует адаптивные веса.

План фиксируется и сохраняется атомарно с выбранными task/seed до предъявления, включая
незавершённые серии. Reload сбрасывает ответы и создаёт новый runId, но воспроизводит тот же план.
Изменение профиля/даты влияет только на явный выбор новой серии. Смена фильтра сводки также не
заменяет активный план и не перезапускает практику.

В сохранении — последние 256 уникальных отпечатков полного порядка высот (20 MIDI-чисел), общих для
всех заданий. Серия попадает в журнал при первом фактическом предъявлении; повторные callbacks не
дублируют запись. Повторный проход переносит отпечаток в конец журнала. Перед поиском проверки
оболочка ждёт загрузки и читает актуальный журнал IndexedDB, затем перебирает seed до неизвестного
порядка с ограничением 4096 кандидатов. При первом показе атомарная транзакция проверяет и обновляет
журнал: только подтверждённый commit неизвестного отпечатка разрешает `newMaterial=true`. Ошибка
чтения/записи, reload известной серии или конкурирующий показ не подтверждают новизну. Если поиск
исчерпан, показывается повторяемая ошибка и новый запуск не объявляется «новым материалом».
Незавершённый проход не становится результатом, но остаётся предъявлением.

### Совместимость хранилища

Используется существующая IndexedDB `piano-trainer`, версия базы 1, object store `settings`, ключ
`reading-course-v2`. Новая база и upgrade схемы IndexedDB не нужны. Корень получает
schemaVersion: 2. Мигратор/валидатор чистые; `readingPersistence.ts` использует существующий
listener и асинхронный адаптер к settings. Успешной считается транзакция oncomplete, не только
запрос put. `reading-course-v1` читается как legacy-источник и остаётся нетронутой резервной копией.
При наличии новой записи IndexedDB имеет приоритет; повторный импорт legacy не дублирует результаты.
Сохраняются prefs/task/seed и старые results; id результата служит runId, attemptId
восстанавливается детерминированно, skillId определяется как чтение пяти нот. createdAt — известное
завершение; startedAt и отсутствующая история помощи — null с provenance legacy, а не пустой журнал,
утверждающий отсутствие помощи. Известные atMs/hintLevel/latency сохраняются.

Из старого exerciseId восстанавливается generatorVersion только при однозначном формате. Известный
v1 позволяет восстановить отпечаток последовательности, но не доказать её новизну. Старые записи
участвуют в доступных метриках; не входят в показатель доказанного переноса на новый материал.
Повторный load/resultAdded не меняет веса или срок повторения повторно.

Неизвестная будущая версия блокирует запись в этот ключ на сеанс, чтобы downgrade не разрушил
данные. Повреждённые results пропускаются с общим уведомлением; валидные настройки/результаты
сохраняются. Профиль держит последние 20 компактных наблюдений на ноту/назначение/источник и
рассчитанные даты; ограничение подробной истории не стирает его. listener пишет только при реальном
persistent изменении, не на кадре/монотонном tick.

Загрузка IndexedDB асинхронна. До её завершения запись заблокирована; позднее восстановление сливает
результаты по runId и не отменяет выбор серии/фильтра/предпочтений, изменённых после начала чтения.
Загрузка не заменяет активную сессию. Ошибка чтения не разрешает перезаписать неизвестное сохранение
defaults; прогресс остаётся в памяти с уведомлением. Записи сериализованы, устаревшие операции не
перезаписывают новый снимок. Миграция подтверждается только commit транзакции.

## Risks / Trade-offs

- Рост истории → IndexedDB, ограниченные журналы/окна, существующий notice при quota; работа в
  памяти.
- Малое число наблюдений → сбалансированный fallback и видимое количество данных.
- Часы устройства меняются → отложенный срок календарный, реакция монотонная; unit-тесты
  отрицательного сдвига даты без изменения музыкального времени.
- Новизна ограничена журналом → явная подпись ограничения, без обещания «никогда не видели».
- Миграция может создать неполные данные → nullable поля/provenance, метрики только из известных
  свидетельств; регрессии P1 и смешанного повреждения.

## Migration Plan

1. После согласования реализовать мигратор и ядро на task branch от актуального dev; сначала tests.
2. Подключить оболочку/локализацию, проверить P1 и все storage failures, выполнить обязательные
   gates.
3. Открыть PR в dev. После пользовательского merge обновить основную папку ff-only и проверить
   localhost:5190, если пользовательский стенд доступен. Агент не запускает сервер без разрешения.
4. При rollback P1 читает сохранённую legacy-копию localStorage, а прогресс после миграции остаётся
   в IndexedDB и доступен после возвращения P2. Двусторонняя синхронизация с P1 не обещается.
