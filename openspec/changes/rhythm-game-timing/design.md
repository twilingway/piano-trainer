## Context

Основа — два документа игрока в `docs/`. Это проект нового поведения; производственная реализация не
начата. Сейчас MIDI timestamp/device отбрасываются, Trainer судит по последнему session.time, а
frame продвигает время через `min(deltaMS, 100)`. ComboCounter и ResultDialog используют старую
формулу Accuracy. TakeRecorder чистый и уже принимает внешние song/real времена; это нужно
сохранить.

## Goals / Non-goals

Цель — воспроизводимые judgement/Score по времени события с единым session clock, калибровкой и
видимыми правилами режима. Не менять исходную партитуру, solver аппликатуры и смысл старого
педагогического разбора. Не добавлять production-зависимости, сетевое хранение профилей, онлайн
рейтинги, Pro/Expression/Latency Assist без отдельной спецификации.

## Decisions

### Владение временем

Чистый `src/practice/timing.ts` хранит сегменты Performance ↔ Song Time и связи с Audio Clock.
PracticeSession владеет таймлайном и принимает внешний монотонный timestamp из Trainer; никаких
performance.now/таймеров в core. Pause/wait дают сегменты с нулевой скоростью, resume/seek/скорость
создают новые anchors. Событие преобразуется по своему сегменту, а не по моменту callback. Rendering
только читает session time; shell отдельно планирует звук и передаёт MIDI.

### Matching и доставка

`judgement.ts` задаёт окна сложности и ближайшую pending-ноту той же высоты. Фиксированный snapshot
offsets применяется один раз перед matching. Предварительный MISS не становится окончательным раньше
принятого горизонта доставки события: необходимы упорядоченная очередь либо транзакционная
пересборка ещё не завершённой оценки. Это защищает от callback, пришедшего после кадра. Предлагаемый
горизонт — 250 мс сверх максимальной положительной input/manual-компенсации. Более старое событие
диагностируется как просроченное, не получает второй Score и не портит запись.

Каждый запуск имеет ID и интервал Performance Time. Seek/restart/Loop создают новый ID; задержанное
событие относится к запуску по исходному timestamp, а не к текущему callback. Финализация проходит
после границы доставки последних атак, закрытия аккордов и завершения Hold; только затем появляется
окончательный результат или начинается новый Loop. Ноты участка выбираются по началу `[from, to)`,
Hold обрезается на `to`, группы аккордов не пересекают границу. При нуле оцениваемых нот
показывается «Нет нот для оценки» без игрового Rank.

### Правила результата

`gameScore.ts`, `chords.ts`, `holds.ts` и `gameResults.ts` чистые: оценки и очки, серии/бонусы,
итоги групп, физические удержания и статистика. Предлагаемый порядок — Combo увеличивается за каждую
ноту до выбора множителя (10-я получает ×2); аккорд группируется от первой ноты, а не транзитивной
цепочкой. PARTIAL закрывается один раз, очки взятых атак остаются; Streak Bonus без множителя
начисляется один раз при достижении порога в серии. GOOD/OK сбрасывают только Flow, не обычный
Combo. Основной weighted Accuracy не включает Hold, velocity и педаль.

### Audio, visual и ввод

Входы получают raw high-resolution timestamps и source/device metadata. Note On velocity 0 равен
Note Off; CC64 получает то же время, но не влияет на стандартную атаку/физическое удержание. Audio
scheduler использует anchor audioContext.currentTime ↔ performance.now, компенсирует положительный
output offset ранним планированием и отменяет старые задания при pause/seek. Look-ahead не проходит
через ожидающий аккорд. Visual Offset применяется только к представлению, не влияет на
status/Score/запись. Raw и corrected значения сохраняются для диагностики.

### Калибровка и сохранение

`calibration.ts` считает median/MAD по 4+24 ударам, выбросы отбрасываются явным правилом и
показывается confidence. Профиль localStorage индексируется device ID + выбранный транспорт; Web
MIDI не предоставляет надёжную автоматическую классификацию USB/BLE. Профили разных подключений не
смешиваются. Нельзя называть median игры под метроном отдельной аппаратной MIDI latency: она
включает человека и слышимый audio путь. Ranked не обучает offset на партии и сохраняет snapshot
правил. Take schema расширяется версией правил и metadata, старые записи остаются доступными без
нового Rank.

Во время калибровки Audio Offset и выбранный аудиовыход фиксированы; профиль сохраняет эту
аудиоконфигурацию. После её изменения требуется повторная проверка эффективной поправки. Web Audio
не всегда сообщает физическую смену системного выхода, поэтому интерфейс даёт явное предупреждение о
повторной калибровке после подключения других наушников или колонок.

### Этапы после решения вопросов

Сначала timestamps/timeline/matching и regression для wait/pause/FPS/запаздывающего callback. Затем
Score/группы/hold/Flow и результаты; потом калибровка/профили/audio/diagnostics и режимы
Practice/Ranked. Каждый этап содержит свои тесты и UI, а не только недоступное из игры ядро.
Детальный implementation checklist будет создан после закрытия Open Questions.

## Risks / Trade-offs

- Старые записанные времена получены по frame clock: их нельзя выдать за новый точный timing.
- Простой параметр timestamp в pressKey не исправляет преждевременный MISS, нужен порядок
  завершения.
- Смена anchor и большой offset могут сделать время Note Off раньше Note On; интервалы должны
  оставаться неотрицательными, события разных устройств различаются по источнику.
- Суммарная статистика калибровки не доказывает отсутствие постоянной ошибки исполнителя.
- Scheduler должен отменять look-ahead на seek/wait; иначе другая рука прозвучит раньше обучения.
- Старые «Точно/Рано/Поздно/Мимо» и Accuracy в активном `note-fx` требуется согласовать до
  завершения.

## Open Questions

Два вопроса отправлены игроку. До ответов следующие значения — предложения, не принятые правила:

1. Overdrive 10 с за 50 Energy либо 20 с; Hold от 500 мс, +10 base за каждый полный интервал 100 мс;
   Flow после 20 PERFECT/GREAT, сброс при GOOD/OK/ошибке. Альтернатива игрока — пока только timing,
   оценки, Score/Combo и калибровка, без расширенной механики этого этапа.
2. Конфликт: GAME_RULES штрафует WRONG NOTE только в активном окне, TIMING_ENGINE — при любом
   отсутствии match. Предлагается активное окно, без штрафов в lead-in/паузах/тишине. Stars
   предлагается считать от идеального Score без Overdrive, с явной подписью эталона; Ranked доступен
   после успешной калибровки и при 100 % скорости. Альтернатива — пока без Stars/Ranked.

После выбора следует обновить нормативные сценарии, документировать формулу эталона и заполнить
implementation tasks. Код нельзя считать реализующим оба исходных документа до этого решения.
