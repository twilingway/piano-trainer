# Design

## Context

См. `proposal.md`. Приложение — статическая сборка Vite. На Mac mini уже работают Docker и Nginx
Proxy Manager для Towerdefander; прокси использует внешнюю сеть `public_net`. GitHub репозиторий
публичный. `src/library` и `src/recording` сохраняют данные в браузере, поэтому origin должен
оставаться постоянным.

## Goals / Non-Goals

**Goals:** Выпускать проверенный `main` без входящего доступа к Mac из GitHub; удерживать или
возвращать последнюю рабочую версию при сбое.

**Non-Goals:** Не переносить клиентские данные на сервер и не менять рендеринг нот, кадровый цикл и
работу OSMD.

## Decisions

1. Многоэтапный Dockerfile собирает сайт на Node 22 и раздаёт `dist` через Nginx. Compose подключает
   единственный контейнер `piano-web` к `public_net` без публикации порта хоста. Один Proxy Host NPM
   направляет `keys.twiling.ru` и `piano.twiling.ru` на `piano-web:80`, включает Let's Encrypt и
   Force SSL. Редиректа между доменами нет: `localStorage` привязан к origin, и перенаправление
   отрезало бы игроков `piano.` от их песен и дублей. Отдельный Node-сервер или `vite preview` не
   нужны.
2. GitHub Actions выполняет `pnpm check` и `pnpm spec:validate` для PR и `main`. Пользовательский
   launchd-агент на Mac опрашивает `main` и статус конкретной проверки, затем локально собирает
   образ по SHA. По аналогии с Towerdefander на Mac нет self-hosted runner: workflow из публичного
   PR не получает доступ к машине.
3. Скрипт выпуска строит новый образ до остановки старого. После переключения проверяет локальный
   `/health` и публичный маркер версии, записывает SHA лишь при успехе; при сбое переключает Compose
   на сохранённый образ. Хранит три последних образа. Первый выпуск допускает локальную проверку до
   настройки DNS/NPM, затем обязателен полный публичный smoke.
4. `index.html` и маркер версии отдаются без долгого кэширования; хешированные ассеты Vite можно
   кэшировать долго. Это снижает риск смешивания HTML и ассетов разных выпусков.
5. Чистые модули сохраняют текущее владение поведением, React/Pixi/OSMD только отображают его.
   Изменение инфраструктурное и не добавляет вычислений в кадровый цикл или рендер нотного стана;
   риск производительности браузера от него отсутствует.

## Risks / Trade-offs

- DNS и выпуск сертификата требуют доступного публичного A-записи и 80/443 → проверка до добавления
  Proxy Host и после.
- Прерывание между сменой контейнеров может дать короткий 502 → проверка публичного адреса и
  автоматический откат.
- Сэмплы и шрифты загружаются из внешних источников → отдельно проверить звук и сеть браузера при
  приёмке.
- GitHub API без токена ограничивает число запросов → проверять статус не чаще раза в пять минут на
  один SHA; ошибка API не разрешает выпуск.

## Migration Plan

1. Создать PR с конфигурацией, получить зелёный CI и влить в защищённый `main`.
2. Создать каталог `~/piano-prod`, checkout репозитория и агент launchd; подключить контейнер к
   существующей `public_net`.
3. Выпустить первую версию и проверить её локально; добавить Proxy Host в NPM и выпустить сертификат
   после появления DNS.
4. Проверить HTTPS, версию, ресурсы и сохранённые данные в браузере. Для ручного восстановления
   выбрать предыдущий тег образа из истории и запустить Compose с ним.
