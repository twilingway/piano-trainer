## Live Blender и MCP: обязательно выполнить entry point

Пользовательский Blender открыт. CLI `tools/hand-rig/bl.py` подключается к **localhost:9876**. Не
путать с прежними экспериментальными серверами/портами. Native Blender MCP в этой сессии не был
доступен, использовался этот CLI. Сначала проверяй `bpy.data.filepath`, сцену, кадр/окно, текущие
modifiers и JSON SHA. Не запускай второй GUI Blender и не закрывай пользовательский.

Проверенные команды из основной папки:

```powershell
python tools/hand-rig/bl.py "$atlasRoot/inspect-live-review.py"
python tools/hand-rig/bl.py "$atlasRoot/run_hud.py"
python tools/hand-rig/bl.py --shot "$atlasWork/resume-review.png" 1400
```

`inspect-live-review.py` читает состояние и сохраняет снимок окна; `run_hud.py` устанавливает
runtime HUD. После рестарта HUD нужно включать снова; сохранённые timeline markers и Text остаются в
blend. Снимок обязательно открыть и посмотреть. Не путать runtime HUD с содержимым frozen-файла.

**Критическая особенность MCP:** код посылается через exec, поэтому `if __name__ == '__main__'`
внутри загружаемого скрипта сам не сработает. Успешная доставка кода не означает запуск работы.
Используй проверенные wrappers, которые явно вызывают `module.main()` или нужную функцию. Для нового
guarded-модуля wrapper имеет такую форму:

```python
import importlib.util
from pathlib import Path
path = Path('ABSOLUTE_PATH_TO_REVIEWED_SCRIPT.py')
spec = importlib.util.spec_from_file_location('atlas_explicit_entry', path)
module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(module)
module.main()
```

Повторно импортируемые модули обновлять через importlib.reload/новое имя. Не посылай параллельные
мутации MCP. После служебных проверок верни кадр, subframe и выбранный вид.

## Воспроизводимый цикл изменения других поз

1. Прочитать актуальный JSON, назначение и `pressed_fingers`; не менять ноты или смысл кадра ради
   красивой формы. Сравнить с последней сценой и её SHA.
2. Сделать отдельные резервные blend/JSON до правки. Подбор вне Blender пишет candidate JSON/NPZ и
   диагностику; прогноз не считать actual-проверкой.
3. Менять только разрешённую правую кинематику: плечо17/локоть19/запястье21 и согласованные
   пальцевые hinge/abduction DOF. Плечо/локоть получать source-consistent IK. **Не редактировать
   вручную raw mesh, rest rig, длины/масштаб костей, масштаб кисти/тела или тело/левую руку.**
   Недостижимую цель отклонять без растяжения.
4. При смене позы пересчитать source correctives/v_posed/LBS, применить позу и подогнать ногти.
   Простое вращение костей со старыми корректировками недопустимо.
5. Обновить `WORK/batch-plan.json`: точный набор кадров, предыдущий JSON, backup blend, candidate
   paths/hashes. `apply-batch.py` проверяет сохранение остальных raw-поз/кривых/объектов. Только
   после ревью плана вызвать live wrapper.
6. Выполнить actual-аудит конечной кожи/ногтей/клавиш и пар пальцев, сохранить frameN-validation;
   проверить правильные контакты и фотографии сверху/сбоку. Положительный зазор ниже консервативного
   запаса не называть проникновением.
7. Перепривязать/проверить PAD/SIDE GN после изменённых исходных поз: их NPZ и реестры зависят от
   source mesh. Не применять прежний delta к другой позе вслепую. Не давать apply-batch затереть
   разрешённые GN; проверить flags/кадровую область.
8. Обновить сохранённые labels/Text, снять новые виды и восстановить пользовательский вид. Только
   затем создавай новую версию индекса и independent replay. Старый замороженный индекс не изменять
   ради нового результата; работать в новой версии.

## Принятые пользовательские замечания

- Кисть должна быть спокойной, без «когтя». Ориентир —
  [Yamaha](https://hub.yamaha.com/music-educators/instruments/piano/piano-pedagogy-even-scales/):
  естественная кривая, свод, нейтральное запястье/предплечье, контакт уголком большого пальца. Это
  качественный ориентир, не измерение точных углов с фотографии и не калибровка анатомии.
- Для 35–38 свободные пальцы должны выглядеть как расслабленный покой кадра1/аналогичный
  перенесённый покой49. Активную цель подбирать только по XY, не менять свободные пальцы ради
  контакта. Пальцы 2/3 ближе; не превращать это в новый широкий веер. Итог этого нового запроса
  проверить в финальном блоке, не предполагать выполненным.
- Веер 1/5 и 1/3/5 кадров 40/42 исправлялся по замечаниям пользователя. Покой49 переиспользует
  **точные 45 finger-параметров** покоя1 с переносом всей руки.
- Для45 несколько вариантов глубины/поворота обсуждались с пользователем. Продолжай последнюю
  фактически применённую позу, не возвращай первую угловатую или старый candidate. Для48
  пальцы/ноготь должны различаться от самой боковой кожи: положительный зазор ногтя — не
  пересечение.
- Кадр50 — пальцы2/3/4 на F#4/G#4/A#4, а не все пять. Подушечки были сдвинуты глубже и запястье
  уточнено; валидируй actual горизонтальные площадки.
- В51 уменьшали сгиб большого пальца/мизинца, большой палец нужен с боковым краем и осевым поворотом
  ногтя. **Подкладывание большого пальца под ладонь отменено пользователем:** возникла путаница E/F,
  текущая нота большого пальца E и назначения не меняются. Не реализуй отменённое движение.
- 44 дополнительно уточнён в r9 и сейчас имеет положительный свободный зазор около0.153мм. 45/48
  после SIDE имеют положительные около0.020/0.017мм; это amber ЗАЗОР при консервативном запасе0.5мм,
  а не skin/key crossing. У SIDE ногтя наблюдался положительный зазор около0.294мм. Эти сведения
  промежуточны, проверить финальную проверку.

## Контракты геометрии: PAD отдельно от SIDE

**Контакт и измерение.** Активная собственная pad: signed gap [−0.5,+1]мм. Остальные поверхности
строгой rigid-модели требуют0.5мм; если gap положительный, но меньше0.5, показывать предупреждение
ЗАЗОР и сохранять строгую причину, не называть это проникновением. Сторона/верх/перед клавиш
различаются. Прежний heightfield завышал боковое проникновение; actual BVH/полная 3D-геометрия —
источник конечного результата. Реальная плоская верхушка после фасок уже номинальной оценки9.8мм
(actual около5.4мм), попадания в расчётный прямоугольник недостаточно. Клавиши опускаются на8мм,
включая чёрные.

**PAD4/5:** прямое разрешение пользователя на расширение конечной контактной площадки. Только
post-Subdivision evaluated-кожа этих двух кадров, Z-only максимум1мм. Максимумы текущего варианта
около0.913/0.910мм; контактная полоса0…0.1мм имеет ненулевую площадь. Source/raw32 позы, rig, ногти,
клавиши, масштаб и оригинальные шесть файлов/поз не меняются. В других49 кадрах GN даёт точный ноль
относительно их текущих кинематических поз. Поэтому нельзя глобально говорить, что все32
evaluated-сетки рабочей версии совпадают с V1: **4/5 — разрешённые evaluated-исключения**.

**SIDE45/48:** post-Subdivision X-only bounded-деформация до2мм, без изменения
костей/поз/ногтей/клавиш. В тесте максимумы около1.50148/2.000мм. Реестр содержит
frame/finger/vertex IDs/core+halo/black MIDI/side. Halo≤4мм по исходной поверхности и только
same-key/same-side от actual side-core; вне реестра кожа не двигается. Actual активный контакт
защищён совместным условием source-pad>0.5 + собственная назначенная клавиша + исходный
gap[−0.5,+1.5]мм. Under-nail guard — дорсальный footprint до2мм. Guards фиксируются до деформации.
Исходный raw-pad атрибут не менять; его незащищённая боковая часть может деформироваться. Все
активные контакты проверяются по исходным pads после dx.

Для зарегистрированного бокового участка actual-зазор≥−1e−6м; вне него сохраняются исходные допуски.
0.02мм — нижняя граница, не аттрактор: изолированный весь свободный patch+0.27мм без сжатого core
должен дать dx0/SIDE_CLEARANCE_ONLY/compression_applied=false. В зарегистрированном плавном halo
положительная точка может смещаться от соседнего сжатого core. Отрицательные контроли исключают
top/front/back/wrong MIDI/opposite side, protected contact/nail/offregistry, side−0.2мм, missing
registry/source/displacement и active contact+8мм. Не менять universal nonpad/rigid допуск ради
PASS.

PAD/SIDE — ограниченная визуально-геометрическая деформация. Нет давления, FEM, физики мягких
тканей, гарантии комфорта или педагогического одобрения. Исторический
`ROOT/lateral-squeeze-study/study-run2/` имел dx0 во всех пробах; его delivery summary прямо говорит
real_compression_demonstrated=false. Не подменяй это поздней SIDE-работой и не переписывай старые
отчёты.

## Публикация и проверки

инструменты и файл layout**; изображения не нужны. Планируемый публичный каталог —
`tools/hand-atlas/atlas-20261019/` (проверить итоговый путь). Это больше, чем документационный PR.

layout безопасно отделяются от licensed-model данных. **Полный private SMPL+H JSON не считается
автоматически разрешённым к публикации.** Не подменяй одобренный экспорт копированием всей
лаборатории.

остаются локальными; полный blend архивируется отдельно. Keyboard-only layout не включает
SMPL-тело/кисть. Для воспроизведения тела на другой машине понадобится отдельно полученная
лицензированная внешняя MANO/SMPL+H модель:
[официальная лицензия](https://mano.is.tue.mpg.de/license.html),

## Следующий продуктовый этап: свой визуал на production-сайте

Пользователь хочет заниматься на production-сайте со своей локальной MANO/SMPL+H-визуализацией, без
запуска dev-сервера. Это следующий отдельный этап, **ещё не реализованный**: текущий атлас не
подключён к игре.

Предполагаемый пользовательский поток: выбрать локальные GLB и pose JSON через file picker,
сохранить их в IndexedDB этого браузера и рисовать в браузере. Модель и её производные файлы не
загружаются на сервер и не попадают в публичный Git. Этот поток не означает, что сайт уже умеет
импортировать локальную модель или воспроизводить этот атлас.

Перед реализацией нужен отдельный OpenSpec: экспорт GLB и pose-track, retarget на runtime-rig,
подключение к игровому renderer и локальный asset import в production. Учесть версию форматов,
сохранение/повторное открытие данных браузера и пользовательские ошибки импорта. Время игры
по-прежнему берётся только из PracticeSession: атлас, руки и музыка читают один clock, новый
загрузчик или анимация не создают второй источник времени.

Текущую задачу не расширять этой production-функцией. Сначала сохранить и передать проверяемые
артефакты атласа; затем отдельно проектировать локальный импорт и runtime-интеграцию.
